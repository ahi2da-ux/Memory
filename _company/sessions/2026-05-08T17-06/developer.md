### 🎯 1. 데이터 Lock 메커니즘 구현 계획 (Phase 1)

**목표:** 포인트 지급 및 MY 탭 업데이트 과정에서 발생하는 비동기 처리(Async)로 인한 잠재적 레이스 컨디션(Race Condition)을 방지하고 트랜잭션의 원자성(Atomicity)을 보장합니다.

#### A. 기술 설계 (Implementation Plan)
1.  **Lock 메커니즘 선택:** Supabase/PostgreSQL 환경에서 가장 안정적인 **Row-Level Locking** 또는 **Transaction Isolation Level** 조정을 기본으로 채택합니다.
2.  **트랜잭션 범위 정의:** 포인트 지급(`points` 테이블 업데이트)과 사용자 탭 정보 업데이트(`my_tabs` 테이블 업데이트)를 하나의 논리적 트랜잭션 블록으로 묶어 처리합니다.
3.  **Lock 적용 시점:**
    *   사용자 요청 수신 시, 관련 레코드(예: `user_id`)에 대해 **FOR UPDATE** 락을 즉시 획득합니다.
    *   포인트 지급 및 데이터 업데이트가 완료될 때까지 해당 락을 유지합니다.
4.  **Rollback 보장:** 트랜잭션 내에서 오류 발생 시, 모든 변경 사항이 롤백되도록 DB 수준의 트랜잭션 관리(ACID)를 엄격하게 적용합니다.

#### B. Phase 1 구체화 (Action Items)
| 단계 | 작업 내용 | 담당 에이전트/팀 | 예상 산출물 | 기한 목표 |
| :--- | :--- | :--- | :--- | :--- |
| **P1.1** | Supabase RLS 및 트랜잭션 격리 레벨(Isolation Level) 검토 및 설정 | Backend / DB 팀 | Isolation Level 변경 적용 계획서 | D+1 |
| **P1.2** | 포인트 지급/MY 탭 업데이트 로직에 `SELECT FOR UPDATE` 구문 삽입 및 테스트 환경 적용 | Developer (Lead) | 핵심 트랜잭션 코드 수정본 | D+2 |
| **P1.3** | Lock 메커니즘 구현 후, 비동기 작업(Queue)과의 인터페이스 안정성 검증 | Data Agent / QA Agent | Lock-Async 통합 테스트 케이스 | D+3 |

### 📊 2. Acceptance Test Case (TC-01~TC-05) E2E 검증 우선순위

데이터 정합성 확보가 P0 목표 달성의 핵심이므로, **'데이터 흐름의 원자성과 불일치 방지'**에 초점을 맞추어 테스트를 우선순위화합니다.

| 우선순위 | Test Case (TC) | 중점 검증 항목 | 목표 리스크 | 이유 및 실행 방법 |
| :--- | :--- | :--- | :--- | :--- |
| **P0 (Critical)** | **TC-05** | 포인트 지급과 MY 탭 업데이트의 동시성 실패 시나리오 재현 및 Rollback 확인. | 데이터 불일치 ($\le$ 0% 달성) | 가장 핵심적인 P0 목표(가치 생성 루프 완성도)와 직결됨. Lock 메커니즘이 정상 작동하는지 최종 검증. |
| **P1 (High)** | **TC-02** | 사용자 로그인/세션 데이터와 포인트 적립 기록 간의 일관성 확인. | 인증 및 권한 오류 | Auth 과정에서 발생하는 세션 정보가 DB에 올바르게 반영되었는지 확인하여 초기 접근 안정성 확보. |
| **P2 (Medium)** | **TC-01** | 사용자 온보딩(로그인 $\to$ 포인트 적립)의 성공률 측정. | 사용자 경험 연속성 | 기본적인 흐름이 막힘없이 진행되는지 확인하여 UX 이탈 지점을 파악. |
| **P3 (Low)** | **TC-03** | 알림 기능과 데이터 업데이트 간의 비동기 처리 시점 차이 분석. | 레이스 컨디션 발생 여부 | Lock 메커니즘 적용 후, 기존 잠재적 문제 영역에 대한 보조 검증 수행. |
| **P4 (Future)** | **TC-04** | 1억 챌린지 관련 데이터 흐름의 최종 승인 로직 테스트. | 수익화 목표 연동 | MVP 출시 이후 단계에서 필요한 고급 기능의 안정성 확보. |
