## E2E 트랜잭션 안정성 통합 테스트 계획

CEO 지시에 따라, 기존의 10가지 E2E QA 시나리오를 확장하여 새로운 번들 및 리워드 흐름에 대한 **트랜잭션 안정성(Lock 메커니즘) 검증**을 포함하는 통합 테스트 케이스를 작성하고 실행 계획을 수립합니다.

### 1. 목표 정의 (P0: 시스템 안정성 확보)
*   **최종 목표:** 새로운 번들/리워드 로직에서 포인트, 구독 상태, 사용자 데이터 업데이트 시점에 Lock 메커니즘이 성공적으로 작동하여 데이터 불일치(Race Condition)가 발생하지 않음을 E2E 관점에서 입증한다.
*   **핵심 검증 대상:** `SELECT FOR UPDATE` 또는 유사한 잠금 메커니즘이 다중 트랜잭션 환경에서 데이터의 원자성과 일관성을 보장하는지 확인한다.

### 2. 기존 QA 시나리오 확장 및 신규 테스트 케이스 설계
기존의 10개 핵심 흐름에 'Lock 안정성' 검증 단계를 추가합니다. (편의상 기존 시나리오를 A~J로 명명)

| ID | 기존 E2E 시나리오 (예시) | Lock 메커니즘 확장 테스트 항목 (신규) | 검증 목표 |
| :---: | :--- | :--- | :--- |
| A | 로그인 및 세션 관리 | **(N/A)** | 기본 인증 안정성 확인 |
| B | 포인트 적립 및 MY 탭 업데이트 | `ポイント_UPDATE` 트랜잭션 중, DB Lock 성공 여부 기록 검증 | 동시 쓰기 환경에서의 데이터 정합성 |
| C | 가격 제보 승인 흐름 | **(Lock on Approval)**: 승인 대기 중 포인트 잠금 테스트 (승인 전/후) | 상태 변경 시점의 Lock 유지 확인 |
| D | 알림 수신 및 리워드 지급 | 리워드 지급 트랜잭션 시작 시, 관련 사용자 데이터에 대한 잠금이 걸리는지 확인 | 지급 작업의 원자성 확보 |
| E | 챌린지 참여 및 완료 | **(Lock on Challenge State)**: 챌린지 상태 변경 중 다른 트랜잭션 간 충돌 테스트 | 챌린지 진행 상태의 안정성 |
| F | 구독/번들 선택 흐름 | **(Lock on Selection)**: 번들 옵션 선택 시, 재고/가격 데이터 잠금 테스트 | 번들 상품 선택의 배타적 권한 확보 |
| G | 수익화 후보 가게 연동 | 포인트 차감 및 상점 데이터 업데이트 동시성 검증 | 외부 데이터 연동 시 Lock 안정성 확인 |
| H | (기존 3가지) | **(통합 Stress Test)**: A, B, C, D 항목을 동시에 병렬 실행하여 Deadlock 또는 데이터 불일치 발생 여부 테스트 | 시스템 전체의 동시성 안정성 검증 |

### 3. 통합 테스트 실행 계획 (Execution Plan)

**Phase 1: 단위 Lock 로직 검증 (Unit Level)**
1.  `point_update_logic` 및 `my_tab_update_logic` 함수 내에서 트랜잭션 시작 시점에 Lock 메커니즘(`SELECT FOR UPDATE`)이 정확히 적용되는지 단위 테스트를 실행한다.
2.  트랜잭션 실패(Rollback) 시, 잠금이 정확하게 해제되는지 확인하는 예외 처리 로직을 검증한다.

**Phase 2: E2E 통합 Lock 검증 (Integration Level)**
1.  **시나리오 기반 테스트:** 위에서 확장된 10개 흐름(A~H)에 대해, 각 단계가 데이터베이스 레벨에서 잠금을 올바르게 수행하고 해제하는지 확인한다.
2.  **Race Condition 시뮬레이션:** 가장 취약하다고 판단되는 지점(예: 포인트 적립과 MY 탭 업데이트 동시 실행)을 대상으로 **병렬 요청(Concurrent Requests)**을 시뮬레이션하여 데이터 불일치가 발생하는지 반복적으로 검증한다.

**Phase 3: 최종 안정성 보고 (Final Verification)**
1.  **테스트 결과 집계:** 모든 테스트 케이스의 성공/실패 여부를 `kpi_log` 또는 별도의 Lock 검증 로그에 기록한다.
2.  **리스크 평가:** 트랜잭션 실패율 및 Deadlock 발생 시나리오 결과를 기반으로, 최종 출시 승인 기준(ROI)에 미치는 잠재적 리스크를 정량화하여 Business 에이전트에게 보고한다.

### 4. 실행 환경 요구사항
*   테스트는 **실제 운영 환경과 유사한 동시성 부하**를 시뮬레이션할 수 있는 테스트 환경에서 진행되어야 한다.
*   모든 Lock 메커니즘의 성공 및 실패 로그는 데이터베이스 레벨에 기록되어야 하며, 이 로그가 E2E 검증 결과와 직접 연결되어야 한다.
