## 데이터 Lock 메커니즘 구현 계획 및 TC-05 원자성 확보 최우선 작업

CEO 지시에 따라 데이터 Lock 메커니즘 구현 계획(P1.2, P1.3)을 즉시 시작하며, Acceptance Test Case (TC-01~TC-05) 중 가장 중요한 부분인 **TC-05 관련 트랜잭션 원자성 확보**를 최우선으로 진행합니다.

### 1. 구현 계획 (P1.2 & P1.3 상세화)

**목표:** Supabase 환경에서 포인트 지급 및 MY 탭 업데이트 과정의 데이터 정합성을 보장하기 위해 트랜잭션 기반의 Lock 메커니즘을 구현합니다.

#### P1.2: 데이터 Lock 메커니즘 설계 (Focus: Atomicity for TC-05)
*   **핵심 목표:** 포인트 지급(쓰기 작업)과 MY 탭 업데이트(읽기/쓰기 작업)가 하나의 원자적 단위로 실행되도록 보장합니다.
*   **구현 방식:** PostgreSQL의 `SELECT FOR UPDATE` 또는 동시성 제어(Concurrency Control)를 활용하여 트랜잭션 내에서 특정 레코드에 대한 배타적 잠금(Exclusive Lock)을 확보합니다.

#### P1.3: 구현 상세 계획 (Developer 주도)
*   **트랜잭션 범위 설정:** 포인트 지급 로직과 MY 탭 업데이트 로직 전체를 하나의 데이터베이스 트랜잭션 블록으로 묶습니다.
*   **Lock 객체 정의:** 포인트 테이블 및 사용자 정보 테이블에 대해 동시성 제어를 위한 Lock 객체를 정의합니다.

### 2. TC-05 원자성 확보를 위한 E2E 검증 우선순위 설정

TC-05 (포인트 지급과 MY 탭 업데이트 간의 비동기 처리에서 발생하는 잠재적 레이스 컨디션)는 가장 높은 ROI 리스크가 있다고 판단되므로, Lock 메커니즘 구현 성공 여부를 이 테스트 케이스의 **최종 승인 기준**으로 설정합니다.

| 단계 | 검증 항목 | 목표 결과 (원자성 확보 기준) | 연결된 Lock 적용 범위 |
| :--- | :--- | :--- | :--- |
| **T-01** | 로그인 및 세션 확인 | 성공적인 인증 흐름 | N/A |
| **T-02** | 권한 확인 (Auth Flow) | 사용자 역할에 따른 접근 제어 성공 | N/A |
| **T-03** | 정보 제보 및 포인트 적립 연동 | 데이터 흐름의 일관성 검증 | Lock 메커니즘 적용 시작 지점 |
| **T-04** | 포인트 지급 후 MY 탭 업데이트 | **Lock으로 보장된 트랜잭션 완료** | **P1.2, P1.3 구현 결과 확인** |
| **T-05** | 최종 데이터 불일치율 검증 | **데이터 정합성 0% 달성 (Race Condition 방지)** | **최종 출시 승인 기준 (P0)** |

### 3. 다음 실행 단계

1.  **DB 스키마 업데이트:** 포인트 및 사용자 테이블에 Lock을 위한 적절한 제약 조건(또는 명시적 잠금 전략)을 반영하는 SQL 스크립트를 작성합니다.
2.  **Lock 구현 (P1.2):** 포인트 지급 API 로직 내부에 `SELECT FOR UPDATE`를 적용하여 트랜잭션의 원자성을 확보하는 코드를 개발합니다.
3.  **E2E 재실행 준비:** Lock 메커니즘이 적용된 상태로 T-05 시나리오에 대한 E2E 테스트 케이스를 실행할 환경을 준비하고, 실패 시 리스크 평가를 즉시 수행할 수 있도록 준비합니다.
