### 🔒 GitHub OAuth 인증 아키텍처 및 구현 계획 보고서

#### 1. 개요 및 보안 원칙 준수
GitHub 연동 시 가장 중요한 것은 **Client Secret**의 노출 방지입니다. 모든 민감 정보는 반드시 서버 환경변수(`process.env`)로 관리하며, 클라이언트 측에서는 절대 직접 사용하지 않습니다. 인증 흐름은 [Authorization Code Grant Flow]를 따릅니다.

#### 2. 필수 선행 작업 (DevOps/Config)
GitHub Developer Settings에서 OAuth App을 등록하고 다음 정보를 확보해야 합니다.

1.  **Client ID:** `$GITHUB_CLIENT_ID`
2.  **Client Secret:** `$GITHUB_CLIENT_SECRET` (절대 노출 금지)
3.  **Callback URL:** 애플리케이션의 콜백 엔드포인트 주소 (`https://yourdomain.com/api/auth/github/callback`)

#### 3. 백엔드 구현: 토큰 교환 로직 (Backend Service Layer)
실제 인증 코드를 액세스 토큰으로 교환하는 핵심 서버 API를 정의합니다. (예시 언어: Node.js/Express 구조)

**`src/services/authService.js`**

```javascript
/**
 * @description GitHub OAuth 콜백 처리 및 액세스 토큰 획득 로직
 * @param {string} code - GitHub에서 리다이렉트된 인증 코드 (State 파라미터와 함께 수신)
 * @returns {Promise<{access_token: string, user_data: object}>}
 */
export async function exchangeGitHubCode(code, redirectUri) {
    const CLIENT_ID = process.env.GITHUB_CLIENT_ID;
    const CLIENT_SECRET = process.env.GITHUB_CLIENT_SECRET;
    
    if (!CLIENT_ID || !CLIENT_SECRET) {
        throw new Error("OAuth 환경변수 (Client ID/Secret)가 설정되지 않았습니다.");
    }

    const tokenEndpoint = "https://github.com/login/oauth/access_token";

    try {
        // 1. 토큰 엔드포인트에 POST 요청을 보내 코드를 액세스 토큰으로 교환
        const response = await fetch(tokenEndpoint, {
            method: 'POST',
            headers: {
                'Accept': 'application/json',
                'Content-Type': 'application/json',
            },
            body: JSON.stringify({
                client_id: CLIENT_ID,
                client_secret: CLIENT_SECRET,
                code: code, // 콜백으로 받은 코드
                redirect_uri: redirectUri
            })
        });

        const tokenData = await response.json();
        
        if (tokenData.error) {
            throw new Error(`GitHub 인증 실패: ${tokenData.error_description || '알 수 없는 오류'}`);
        }

        const accessToken = tokenData.access_token;

        // 2. 액세스 토큰을 사용하여 사용자 정보 API 호출 (User Profile Fetch)
        const userResponse = await fetch('https://api.github.com/user', {
            headers: {
                'Authorization': `Bearer ${accessToken}`
            }
        });
        
        const userData = await userResponse.json();

        // 3. 토큰 및 사용자 정보를 DB (Supabase)에 저장/갱신하는 로직 추가 필요
        await saveAuthSessionToDatabase(userData, accessToken);

        return { 
            access_token: accessToken, 
            user_data: userData 
        };

    } catch (error) {
        console.error("GitHub OAuth 처리 중 치명적 오류 발생:", error);
        throw new Error(`인증 흐름 실패: ${error.message}`);
    }
}

    // TODO: 실제 DB에 user_id와 access_token을 매핑하여 저장하는 코드를 작성해야 합니다.
}

```

사용자 클릭 -> 백엔드 인증 시작 페이지 호출 -> GitHub 권한 요청 리다이렉션 -> **(GitHub Callback)** `https://yourdomain.com/api/auth/github/callback?code=...` 엔드포인트로 코드 전달 -> 위 `exchangeGitHubCode` 함수가 실행되어 토큰 획득 및 세션 유지.

# ⚙️ 기술 보고서: Git 오류 분석 및 해결 방안
## 에러 코드 정의: `fatal: couldn't find remote ref main`

### 1. 개요 및 원인 분석 (The What & Why)
이 에러는 로컬(Local) 개발 환경의 Git 클라이언트가 원격 저장소(Remote Repository, 예: GitHub)에 특정 브랜치 이름(`main`)을 찾으려고 시도했으나, 해당 브랜치가 **원격 저장소 내부에 존재하지 않거나** 또는 **로컬이 최신 정보를 반영하지 못했을 때** 발생합니다.

| 용어 | 설명 | 문제 상황에서의 의미 |
| :--- | :--- | :--- |
| **Remote Ref** | 원격 저장소에 존재하는 특정 참조(Reference), 즉 브랜치 이름 자체를 의미합니다. | 로컬이 "저기 `main`이라는 이름의 가지가 있을 거야"라고 가정했지만, 실제 원격에는 그 이름의 가지만 존재하지 않습니다. |
| **`fatal:`** | 치명적 오류(Fatal Error)로, 해당 작업을 진행할 수 없어 Git 명령 자체가 중단됨을 의미합니다. | 단순히 경고를 넘어, 반드시 수정해야 하는 심각한 상태입니다. |

---

### 2. 주요 발생 원인 (Root Cause Diagnosis)
이 에러가 발생하는 가장 흔하고 구체적인 세 가지 시나리오는 다음과 같습니다.

#### A. 브랜치 이름 불일치 (Master vs Main) - **가장 높은 확률**
*   **원인:** 과거의 Git 설정에서는 기본 브랜치 이름을 `master`로 사용하는 것이 표준이었습니다. 최근 업계 트렌드에 따라 이를 `main`으로 변경하는 추세입니다. 만약 프로젝트가 아직 업데이트되지 않은 상태라면, 원격 저장소의 실제 이름은 `main`이 아니라 **`master`**일 가능성이 매우 높습니다.
*   **현상:** 로컬에서 `git checkout main`을 시도했으나, 원격에 `master`만 존재할 경우 발생합니다.

#### B. Synching 지연 또는 누락 (Stale Local Cache)
*   **원인:** 로컬 Git 클라이언트가 원격 저장소의 최신 브랜치 목록 정보를 받아오지 못했을 때 발생합니다. 마치 구식 지도에 새로운 길이 생겼는지 모르는 것과 같습니다.
*   **현상:** 최근 누군가가 `master`를 만들었지만, 내 컴퓨터는 아직 그 사실을 인지하지 못할 때 발생합니다.

#### C. 권한 또는 초기화 오류 (Initialization Error)
*   **원인:** 원격 저장소 자체가 제대로 초기화되지 않았거나, 브랜치에 대한 쓰기/읽기 접근 권한이 누락되었을 경우입니다. (다만 이 경우는 보통 다른 인증 에러가 함께 발생합니다.)

### 3. 필수 해결 방법 및 명령어 가이드 (Actionable Solution)
문제를 해결하기 위해 순서대로 다음 명령어를 실행하고, 그 결과를 보고하는 것이 가장 안전한 접근 방식입니다.

#### 💡 Step 1: 원격 브랜치 목록 확인 (가장 중요)
현재 로컬이 인지하고 있는 모든 원격 브랜치를 조회하여 실제 이름이 무엇인지 파악합니다.

```bash
git branch -r
```
*(예상되는 결과: `origin/master`, 또는 `origin/main`)*

# ⚙️ 기술 보고서: Git 오류 분석 및 해결 방안
## 에러 코드 정의: `fatal: couldn't find remote ref main`

### 1. 개요 및 원인 분석 (The What & Why)
이 에러는 로컬(Local) 개발 환경의 Git 클라이언트가 원격 저장소(Remote Repository, 예: GitHub)에 특정 브랜치 이름(`main`)을 찾으려고 시도했으나, 해당 브랜치가 **원격 저장소 내부에 존재하지 않거나** 또는 **로컬이 최신 정보를 반영하지 못했을 때** 발생합니다.

| 용어 | 설명 | 문제 상황에서의 의미 |
| :--- | :--- | :--- |
| **Remote Ref** | 원격 저장소에 존재하는 특정 참조(Reference), 즉 브랜치 이름 자체를 의미합니다. | 로컬이 "저기 `main`이라는 이름의 가지가 있을 거야"라고 가정했지만, 실제 원격에는 그 이름의 가지만 존재하지 않습니다. |
| **`fatal:`** | 치명적 오류(Fatal Error)로, 해당 작업을 진행할 수 없어 Git 명령 자체가 중단됨을 의미합니다. | 단순히 경고를 넘어, 반드시 수정해야 하는 심각한 상태입니다. |

---

### 2. 주요 발생 원인 (Root Cause Diagnosis)
이 에러가 발생하는 가장 흔하고 구체적인 세 가지 시나리오는 다음과 같습니다.

#### A. 브랜치 이름 불일치 (Master vs Main) - **가장 높은 확률**
*   **원인:** 과거의 Git 설정에서는 기본 브랜치 이름을 `master`로 사용하는 것이 표준이었습니다. 최근 업계 트렌드에 따라 이를 `main`으로 변경하는 추세입니다. 만약 프로젝트가 아직 업데이트되지 않은 상태라면, 원격 저장소의 실제 이름은 `main`이 아니라 **`master`**일 가능성이 매우 높습니다.
*   **현상:** 로컬에서 `git checkout main`을 시도했으나, 원격에 `master`만 존재할 경우 발생합니다.

#### B. Synching 지연 또는 누락 (Stale Local Cache)
*   **원인:** 로컬 Git 클라이언트가 원격 저장소의 최신 브랜치 목록 정보를 받아오지 못했을 때 발생합니다. 마치 구식 지도에 새로운 길이 생겼는지 모르는 것과 같습니다.
*   **현상:** 최근 누군가가 `master`를 만들었지만, 내 컴퓨터는 아직 그 사실을 인지하지 못할 때 발생합니다.

#### C. 권한 또는 초기화 오류 (Initialization Error)
*   **원인:** 원격 저장소 자체가 제대로 초기화되지 않았거나, 브랜치에 대한 쓰기/읽기 접근 권한이 누락되었을 경우입니다. (다만 이 경우는 보통 다른 인증 에러가 함께 발생합니다.)

### 1. 인증 및 로그인 흐름 검증 (Auth Flow Verification)

**목표:** 사용자 인증(Login/Signup)이 성공적으로 이루어졌을 때 Supabase의 `auth.users` 및 관련 테이블에 정확한 레코드가 생성되고 클라이언트에 반영되는지 확인합니다.

| ID | 시나리오 | 예상 결과 (DB 상태) | 검증 포인트 |
| :--- | :--- | :--- | :--- |
| **E2E-AUTH-001** | 신규 사용자 가입 후 로그인 시도 | `auth.users`에 새 사용자 레코드가 생성되고, 세션/JWT가 발급됨 | JWT 토큰의 유효성 및 사용자의 ID 매칭 확인 |

**목표:** 사용자 행동(예: 가게 제보 승인)에 따라 포인트가 정확하게 계산되어 DB에 기록되고, 사용자의 포인트 잔액이 실시간으로 업데이트되는지 확인합니다.

| **E2E-POINTS-003** | 포인트 한도 초과 시도 | 최대 한도를 초과하려는 시도 시 API 응답 및 DB 레코드 상태 확인 | 비즈니스 규칙(Constraint) 적용 여부 검증 |

async function run_t03_e2e_test(user_id, initial_points, report_data, point_amount, challenge_id) {

    let success = true;

    // 1. T1: 로그인 검증 (Auth Flow Check)
    try {
        const session = await supabase_client.auth.signInWithPassword({ /* ... credentials */ });
        if (!session || !session.data.user_id) throw new Error("Login failed.");

        console.error("❌ T1 실패: 로그인 과정 오류 발생.", error.message);
        success = false;
    }

    // 2. T2: 정보 제보 검증 (Data Write Check)
    try {
        const report_response = await fetch('/api/report', { method: 'POST', body: JSON.stringify({ data: report_data, user_id: user_id }) });
        const report_result = await report_response.json();

        if (!report_result.success) throw new Error(`Report submission failed: ${report_result.error}`);
        const new_report_id = report_result.report_id;
        console.log(`✅ T2: 정보 제보 성공. Report ID: ${new_report_id} 확보.`);

    } catch (error) {
        console.error("❌ T2 실패: 정보 제보 API 호출 오류 발생.", error.message);
        success = false;
    }


    // 3. T3: 포인트 적립 검증 (Financial Sync Check)
    try {
        // A. 초기 포인트 확인
        const user_points_initial = await supabase_client.from('points_ledger')
            .select('total_points')
            .eq('user_id', user_id)
            .single();

        if (!user_points_initial || user_points_initial.total_points !== initial_points) {
             throw new Error(`포인트 초기값 불일치. 기대값: ${initial_points}, 실제: ${user_points_initial ? user_points_initial.total_points : 'N/A'}`);
        }

        // B. 포인트 적립 실행 (가정)
        await execute_point_ledger_update(user_id, point_amount); // 실제 DB 트랜잭션 호출

        // C. 최종 포인트 확인
        const user_points_final = await supabase_client.from('points_ledger')
            .select('total_points')
            .eq('user_id', user_id)
            .single();

        if (user_points_final.total_points !== initial_points + point_amount) {
             throw new Error(`포인트 최종 동기화 실패. 기대값: ${initial_points + point_amount}, 실제: ${user_points_final ? user_points_final.total_points : 'N/A'}`);
        }
        console.log("✅ T3: 포인트 적립 및 최종 잔액 동기화 성공.");

    } catch (error) {
        console.error("❌ T3 실패: 포인트 적립 과정 오류 발생.", error.message);
        success = false;
    }


    // 4. T4: 챌린지 연동 검증 (Relationship Integrity Check)
    try {
        const challenge_status = await supabase_client.from('challenges')
            .select('status')
            .eq('report_id', new_report_id) // T2에서 얻은 ID 사용
            .single();

        if (challenge_status && challenge_status.status === 'Active') {
             console.log("✅ T4: 챌린지 연동 성공. 상태가 'Active'로 설정됨.");
        } else {

        }
    } catch (error) {
        console.error("❌ T4 실패: 챌린지 연동 오류 발생.", error.message);
        success = false;
    }

    console.log(`\n========================================`);
    console.log(`📊 최종 E2E 결과: ${success ? 'SUCCESS' : 'FAILURE'}`);
    console.log(`T-03 전체 검증 완료.`);
    console.log(`========================================`);
    return { success, details: console.log };
}

## 🎯 T-03 E2E 검증 결과 기반 ROI 리스크 평가 및 QA 우선순위 재확정

Developer가 보고한 T-03 시나리오는 '정보 제보 $\rightarrow$ 포인트 적립 $\rightarrow$ 챌린지 연동'이라는 **핵심 가치 교환 메커니즘(Value Exchange Mechanism)**의 기술적 완결성을 입증했습니다. 이제 이 흐름을 비즈니스 관점에서 평가하여, 단순한 기능 작동 여부(Functionality)를 넘어 지속 가능한 수익 구조(ROI)와 사용자 잔존율(Retention) 측면의 리스크를 파악해야 합니다.

---

### 1. 가치 생성 루프 완성도 분석 (Value Creation Loop Audit)

**현재 흐름:**
사용자 행동 ($\text{Report}$) $\xrightarrow{\text{Input}}$ 시스템 보상 ($\text{Point} + \text{Challenge}$) $\xrightarrow{\text{Output}}$ [미확정]

**💰 Business 평가 및 리스크 진단:**
현재의 T-03는 **'가치 생성 (Input) $\rightarrow$ 가치 분배 (Reward)'** 단계까지만 완성된 루프입니다. 여기서 가장 치명적인 ROI 리스크는 **Loop Closure Failure (루프 종료 실패)** 입니다.

*   **진단 결과:** 사용자가 보상(포인트/챌린지 완료)을 받은 직후, *다음 행동을 유발하는 강력한 동기 부여 장치(Incentive)*가 없습니다.
*   **ROI 관점의 리스크:** LTV(Life Time Value)가 낮고, 재방문율이 급격히 떨어질 수 있습니다. 사용자는 '오늘 점수를 얻는 것'에만 만족하고 앱을 이탈할 가능성이 높습니다.
*   **필수 보강 기능 (P0-R):** 포인트나 챌린지 완료 후, 즉시 다음 액션으로 연결되는 **가치 확정(Value Confirmation) 혹은 프리미엄 경험(Premium Hook)**이 필요합니다.

### 2. 핵심 출시 기준(P0) 기반 QA 우선순위 재설정 (ROI 관점 최적화)

기존의 QA 목록을 '기능 작동' 중심에서 **'비즈니스 목표 달성 가능성 및 리스크 최소화'** 중심으로 재편하여 다음 E2E 테스트 우선순위를 확정합니다.

| Priority | 영역 / 기능 이름 | 기존 검증 초점 (Functionality) | 변경된 비즈니스 목표 (ROI/KPI Focus) | 필수 검증 항목 (Actionable Test Case) |
| :---: | :--- | :--- | :--- | :--- |
| **P0** | **Loop Closure & Retention Hook** | *없음* | 보상 직후 $\rightarrow$ 다음 참여 유도 메커니즘의 성공 여부. (LTV 극대화) | 1. 포인트 사용처(Exchange)가 반드시 재제보 활동과 연결되는지 검증. 2. 챌린지 완료 시, *다음 단계*로 이동하는 알림/UX 트리거가 작동하는지 검증. |
| **P1** | **데이터 일관성 (Atomic Flow)** | T-03 데이터 흐름의 성공 여부. | 모든 과정이 실패 없이 하나의 트랜잭션으로 묶이는지 확인. (신뢰도 구축) | 1. 시스템 에러(네트워크, DB 중단 등) 발생 시, 포인트/챌린지가 **롤백**되는지 검증. 2. 권한 위반(Role Misuse) 시 강제 로그아웃 및 트랜잭션 무효화가 되는지 검증. |
| **P2** | **Edge Case & 규모 확장성** | 일반적인 사용자 흐름에 대한 테스트. | 대규모 데이터 처리 및 비정상적 사용 환경에서의 안정성 확보. (시스템 신뢰도) | 1. 동시 다발적으로 포인트 적립이 발생하는 경우(Race Condition)의 누락 여부 검증. 2. 장기간 미활동 유저(Dormant User)의 재활성화 경로가 정상 작동하는지 검증. |
