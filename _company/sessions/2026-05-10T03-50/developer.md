### 1. E2E QA 시나리오 확장 및 작성

트랜잭션 안정성(Lock 메커니즘)을 기반으로 로그인/Auth 및 포인트 흐름에 대한 데이터 무결성 검증을 위한 E2E 테스트 케이스 목록을 확장하여 작성합니다. 이 목록은 모든 신규 기능이 데이터 정합성을 보장하는지 검증하는 데 초점을 맞춥니다.

**확장된 Acceptance Test Cases (E2E QA 시나리오)**

| ID | 모듈/흐름 | 테스트 시나리오 (Action) | 예상 결과 (Expected Result) | 핵심 검증 항목 | 관련 로직 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **TC-01** | Auth Flow | 유효하지 않은 자격 증명으로 로그인 시도 | 에러 메시지 반환 및 세션 생성 실패 | 인증 오류 처리 | Auth/Supabase |
| **TC-02** | Auth Flow | 유효한 자격 증명으로 성공적으로 로그인 (최초) | 세션 토큰 발급 및 사용자 데이터 로드 성공 | 세션 및 권한 확인 | Auth/Supabase |
| **TC-03** | Point 적립 (Lock) | A 사용자가 포인트 적립 요청 중 `SELECT FOR UPDATE` 잠금 시작 | DB 트랜잭션이 Lock 상태로 진입 | Lock 메커니즘 초기 활성화 | Point Logic |
| **TC-04** | Point 적립 (Lock) | B 사용자가 동일한 포인트 업데이트를 시도 (경합 상황) | B의 요청은 A의 트랜잭션 완료 대기 | 동시성 제어 성공 | Lock 메커니즘 |
| **TC-05** | MY 탭 업데이트 (Lock) | 포인트 지급 후, MY 탭 데이터베이스 기록 업데이트 시도 | 두 작업(포인트/MY 탭)이 원자적으로 처리되어야 함 | 트랜잭션 원자성 확보 | Point & MY Tab Logic |
| **TC-06** | Negative Test | Lock 메커니즘을 우회하여 동시 요청을 강제 실행 (Stress Test) | 데이터 불일치 발생 또는 Lock 실패 오류 반환 | Lock 메커니즘의 방어력 검증 | Lock Mechanism |
| **TC-07** | Point 지급 (실패) | 포인트 적립 중 외부 API 호출 실패 시도 | 트랜잭션 롤백 및 포인트 미적립 상태 유지 | 실패 시 데이터 무결성 보장 | Transaction Rollback |
| **TC-08** | 알림 시스템 | 포인트 지급 성공 후, 사용자에게 알림 발송 요청 | 알림 메시지가 정상적으로 전송되고 기록됨 | 이벤트/알림 연동 검증 | Notification Service |
| **TC-09** | 챌린지 연동 | 1억 챌린지 달성 조건 충족 시, 포인트 지급 로직 실행 | 챌린지 상태와 포인트 적립이 동시에 성공해야 함 | 복합 트랜잭션 안정성 | Challenge & Point Logic |
| **TC-10** | 데이터 정합성 (Audit) | 모든 트랜잭션 발생 시점의 `kpi_log` 테이블 기록 확인 | 모든 KPI 변수가 NULL 없이 정확하게 로깅됨 | 데이터 무결성 및 추적 | KPI Logging |
| **TC-11** | 구독/번들 적용 | 하이브리드 번들(C) 적용 시, 관련 포인트 차감 및 MY 탭 상태 변경 | 모든 연관 데이터의 상태가 일치함 | 수익 모델 연동 안정성 | Bundle Logic |
