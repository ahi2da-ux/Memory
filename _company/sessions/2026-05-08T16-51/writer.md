## 🧪 Acceptance Test Case (ATC) 초안
**테스트 케이스 ID:** ATC-ASYNC-003
**제목:** 포인트 지급(Point Crediting) 완료 직후 MY 탭의 데이터 정합성 검증 (Race Condition 시나리오 재현)
**목표:** 비동기적으로 처리되는 '포인트 적립 성공' 이벤트가 발생한 후, 클라이언트 측이 즉시 데이터를 요청할 경우, 최신 포인트 잔액 및 거래 내역이 지연되거나 누락되지 않고 정확하게 반영되는지 검증한다.

---

### 🟢 전제 조건 (Pre-conditions)
1.  **사용자 상태:** 테스트 사용자 A가 시스템에 로그인되어 있으며, 현재 포인트 잔액(`Current_Points`)이 100점 이상으로 설정되어 있어야 한다.
2.  **환경:** 개발/스테이징 환경에서 비동기 데이터 처리 로직(Job Queue)과 클라이언트의 실시간 데이터 Fetch API 호출을 동시에 테스트할 수 있는 환경이 준비되어야 한다.

### 🟡 테스트 시나리오 (Test Steps: Race Condition 유발 과정)
| 단계 | 주체 | 동작/액션 | 발생 시간 지연 (Delay) | 목적 및 가정 |
| :--- | :--- | :--- | :--- | :--- |
| **Step 1** | 사용자 A | 특정 매장에서 포인트 적립 활동을 완료하고, 서버에 포인트 지급 요청 API를 호출한다. | N/A | `Point_Earning` 트랜잭션 시작 (비동기 작업 Queue 등록). |
| **Step 2** | 시스템 Backend | Point Earning Job이 백그라운드에서 실행되어 포인트 계산 및 DB 업데이트(`Update_Points`) 작업을 시작한다. | T+0ms | *핵심 비동기 처리 과정.* 이 단계는 완료되는 데 시간이 걸린다고 가정 (예: 500ms). |
| **Step 3** | 사용자 A (클라이언트) | Step 1 호출 직후, 포인트를 즉시 확인하기 위해 MY 탭의 메인 데이터 Fetch API를 호출한다. | T+50ms ~ T+200ms | *Race Condition 유발 시점.* 포인트 DB 업데이트가 완료되기 전에 클라이언트가 데이터를 조회하는 상황을 강제 발생시킨다. |
| **Step 4** | 시스템 Backend | Step 3의 데이터 Fetch API 호출이 실행된다. (읽기 트랜잭션) | T+250ms | 시스템은 현재까지 저장된 포인트 잔액과 거래 내역을 반환한다. |

### 🔴 예상 결과 (Expected Results - Pass Criteria)
1.  **포인트 잔액 정합성:** MY 탭의 '현재 포인트 잔액' 필드는 최종 Point Earning Job이 완료된 시점의 **최종 포인트 합계**를 보여야 한다. (지연되거나 누락된 값이 아닌, 가장 최신 값이어야 함).
2.  **거래 내역 반영:** MY 탭의 '최근 활동 거래 내역' 섹션에는 Point Earning Job이 완료되어 생성된 **새로운 포인트 적립 건**이 필터링 없이 바로 표시되어야 한다.
3.  **시스템 응답:** Step 4에서 데이터 Fetch API가 호출되었을 때, 시스템은 데이터를 임시로 '읽기 전용'으로 처리하며 오류(Error)를 반환해서는 안 되며, **충분한 대기 시간 후 정확한 최종 상태의 데이터**를 성공적으로 제공해야 한다.

### ⚫ 실패 조건 (Failure Conditions - Race Condition Detection)
1.  MY 탭이 포인트 적립 건에 대한 정보를 표시하지 못하고 '데이터 로딩 중' 상태에서 무한정 머무르거나, **Step 3 시점의 초기 포인트 잔액(100점)**을 그대로 보여주는 경우.
2.  포인트가 성공적으로 지급되었음에도 불구하고, MY 탭 내의 거래 내역에 해당 적립 건이 누락되는 경우. (데이터 업데이트 지연으로 인한 조회 실패)

---
**기술적 참고 사항:** 이 테스트 케이스는 `Read/Write` 트랜잭션 간의 시간차(Time Gap)를 활용하여 데이터 정합성 문제를 검증하는 것이 핵심입니다. 따라서, Backend에서 읽기 요청이 들어왔을 때 **가장 최근에 확정된 값으로 강제 동기화**시키는 Lock 메커니즘 또는 CQRS 패턴 도입 여부를 테스트해야 합니다.
