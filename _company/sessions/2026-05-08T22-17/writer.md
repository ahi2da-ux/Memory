### 💡 목표 설정 (Goal Definition)

본 문서는 Business 에이전트가 정의한 KPI와 LTV 예측 모델링 결과를 기반으로, 앱의 핵심 경제 루프인 **[1. 포인트 적립]**과 **[2. 잔액/포인트 사용]** 과정에서 발생 가능한 모든 예외 상황(Negative Case)과 대규모 동시 접속 환경에서의 성능 안정성(Performance Load Test)을 검증하기 위해 작성되었습니다.

특히, `SELECT FOR UPDATE` 및 트랜잭션 원자성 확보가 필수적인 영역에 집중합니다.

### ❌ Part 1: Negative Test Cases (예외/오류 상황 테스트)

| ID | 기능 모듈 | 시나리오 (Test Steps) | 전제 조건 (Pre-conditions) | 기대 결과 (Expected Result) | 검증 초점 |
| :---: | :--- | :--- | :--- | :--- | :--- |
| **NTC-01** | 포인트 사용/차감 | 잔액이 부족한 상태에서 상품 교환 요청. | 1. 유저 A의 현재 포인트 잔액 = 50P. 2. 상품 B의 요구 포인트 = 100P. | 시스템은 "포인트가 부족합니다"라는 명확한 에러 메시지를 반환하며, **잔액 변경(차감) 자체가 발생하지 않아야 함.** (롤백 확인) | 잔액 검증 로직 및 원자성 |
| **NTC-02** | 포인트 적립/제보 | 유효하지 않은 데이터로 포인트 제보 요청. | 1. '장소 ID' 필드에 숫자 외 문자열 전송 시도. 2. 필수값(가격, 거리 등)을 누락하여 제출. | 시스템은 클라이언트 측 및 서버 측에서 상세한 오류 메시지("필수 정보를 입력해주세요")를 반환하며, **포인트 적립 로직 호출 자체가 막혀야 함.** | 유효성 검증 (Validation) |
| **NTC-03** | 결제/교환 취소 | 포인트로 교환된 상품을 사용자가 임의로 취소 요청. | 1. 포인트 사용 완료 후, 즉시 재접속하여 '취소' API 호출 시도. | 시스템은 "이미 거래가 완료되어 취소가 불가능합니다" 메시지를 반환하고, **포인트 및 잔액에 아무런 변화도 없어야 함.** (Double Spending 방지) | 비즈니스 로직 보호 |
| **NTC-04** | 회원 정보 변경 | 관리자 권한 없이 민감 정보를 수정할 때. | 1. 일반 유저 계정으로 다른 사용자의 ID/이메일 등을 임의로 수정 요청. | 시스템은 "권한이 없습니다"라는 메시지를 반환하며, **수정 시도는 거부되어야 함.** (인가(Authorization) 체크) | 접근 통제 및 보안 |

### 🚀 Part 2: Performance Load Testing Items (성능 부하 테스트 항목)

| ID | 영역 | 시나리오 (Test Scenario) | 부하 조건 (Load Condition) | 검증 지표 (KPI Focus) | 목표 SLA (Service Level Agreement) |
| :---: | :--- | :--- | :--- | :--- | :--- |
| **PLT-01** | 트랜잭션 원자성 | 포인트 적립 및 잔액 차감을 동시에 여러 요청이 발생. | 50명의 유저가 3초 동안 초당 평균 10회씩, 포인트 적립/차감 API를 연속 호출 (Race Condition 모사). | **트랜잭션 성공률 100%** (데이터 불일치 없음), 응답 시간(Latency)의 편차 최소화. | 99th Percentile 응답 시간 ≤ 500ms, 데이터 정합성 유지 필수. |
| **PLT-02** | 로그인/인증 | 대규모 동시 접속 및 재로그인 시도. | 1분 동안 500명의 가상 유저가 무작위로 로그인을 시도하거나 세션 만료 후 재접속을 반복. | API 서버의 부하 처리 능력, Rate Limiting 정책 작동 여부 (무한 호출 방지). | 에러 코드 발생률 < 0.1%, 평균 응답 시간 ≤ 300ms. |
| **PLT-03** | 데이터 제출/저장 | 사용자들이 짧은 시간 내에 대량의 '짠테크 장소 정보'를 제보함. | 5분 동안 200개의 API 엔드포인트 요청(POST / submit_place)을 분산하여 전송. | DB 쓰기 성능 (Write Throughput), 데이터 승인/처리 백그라운드 작업 부하 관리 여부. | 초당 처리 가능한 트랜잭션 수 (TPS) 측정, 시스템 자원 고갈 없음 확인. |

---
**[핵심 요청 사항]**

1.  **롤백 검증:** 모든 금융 관련 API(적립/차감) 호출 시, 실패(NTC-01 등)가 발생하면 **반드시 트랜잭션이 완전히 롤백되고 이전 상태로 돌아가는지** 로그를 통해 입증해야 합니다.
2.  **Rate Limiting 구현:** PLT-02 항목에 대응하여 무차별적인 API 호출을 막는 서버 레벨의 속도 제한(Rate Limit) 로직을 적용해 주십시오.
