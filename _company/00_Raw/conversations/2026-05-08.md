### 🔒 GitHub OAuth 인증 아키텍처 및 구현 계획 보고서

#### 1. 개요 및 보안 원칙 준수
GitHub 연동 시 가장 중요한 것은 **Client Secret**의 노출 방지입니다. 모든 민감 정보는 반드시 서버 환경변수(`process.env`)로 관리하며, 클라이언트 측에서는 절대 직접 사용하지 않습니다. 인증 흐름은 [Authorization Code Grant Flow]를 따릅니다.

#### 2. 필수 선행 작업 (DevOps/Config)
GitHub Developer Settings에서 OAuth App을 등록하고 다음 정보를 확보해야 합니다.

1.  **Client ID:** `$GITHUB_CLIENT_ID`
2.  **Client Secret:** `$GITHUB_CLIENT_SECRET` (절대 노출 금지)
3.  **Callback URL:** 애플리케이션의 콜백 엔드포인트 주소 (`https://yourdomain.com/api/auth/github/callback`)

#### 3. 백엔드 구현: 토큰 교환 로직 (Backend Service Layer)
실제 인증 코드를 액세스 토큰으로 교환하는 핵심 서버 API를 정의합니다. (예시 언어: Node.js/Express 구조)

**`src/services/authService.js`**

```javascript
/**
 * @description GitHub OAuth 콜백 처리 및 액세스 토큰 획득 로직
 * @param {string} code - GitHub에서 리다이렉트된 인증 코드 (State 파라미터와 함께 수신)
 * @returns {Promise<{access_token: string, user_data: object}>}
 */
export async function exchangeGitHubCode(code, redirectUri) {
    const CLIENT_ID = process.env.GITHUB_CLIENT_ID;
    const CLIENT_SECRET = process.env.GITHUB_CLIENT_SECRET;
    
    if (!CLIENT_ID || !CLIENT_SECRET) {
        throw new Error("OAuth 환경변수 (Client ID/Secret)가 설정되지 않았습니다.");
    }

    const tokenEndpoint = "https://github.com/login/oauth/access_token";

    try {
        // 1. 토큰 엔드포인트에 POST 요청을 보내 코드를 액세스 토큰으로 교환
        const response = await fetch(tokenEndpoint, {
            method: 'POST',
            headers: {
                'Accept': 'application/json',
                'Content-Type': 'application/json',
            },
            body: JSON.stringify({
                client_id: CLIENT_ID,
                client_secret: CLIENT_SECRET,
                code: code, // 콜백으로 받은 코드
                redirect_uri: redirectUri
            })
        });

        const tokenData = await response.json();
        
        if (tokenData.error) {
            throw new Error(`GitHub 인증 실패: ${tokenData.error_description || '알 수 없는 오류'}`);
        }

        const accessToken = tokenData.access_token;

        // 2. 액세스 토큰을 사용하여 사용자 정보 API 호출 (User Profile Fetch)
        const userResponse = await fetch('https://api.github.com/user', {
            headers: {
                'Authorization': `Bearer ${accessToken}`
            }
        });
        
        const userData = await userResponse.json();

        // 3. 토큰 및 사용자 정보를 DB (Supabase)에 저장/갱신하는 로직 추가 필요
        await saveAuthSessionToDatabase(userData, accessToken);

        return { 
            access_token: accessToken, 
            user_data: userData 
        };

    } catch (error) {
        console.error("GitHub OAuth 처리 중 치명적 오류 발생:", error);
        throw new Error(`인증 흐름 실패: ${error.message}`);
    }
}

    // TODO: 실제 DB에 user_id와 access_token을 매핑하여 저장하는 코드를 작성해야 합니다.
}

```

#### 4. 프론트엔드 흐름 (Frontend Flow)
사용자 클릭 -> 백엔드 인증 시작 페이지 호출 -> GitHub 권한 요청 리다이렉션 -> **(GitHub Callback)** `https://yourdomain.com/api/auth/github/callback?code=...` 엔드포인트로 코드 전달 -> 위 `exchangeGitHubCode` 함수가 실행되어 토큰 획득 및 세션 유지.

# ⚙️ 기술 보고서: Git 오류 분석 및 해결 방안
## 에러 코드 정의: `fatal: couldn't find remote ref main`

### 1. 개요 및 원인 분석 (The What & Why)
이 에러는 로컬(Local) 개발 환경의 Git 클라이언트가 원격 저장소(Remote Repository, 예: GitHub)에 특정 브랜치 이름(`main`)을 찾으려고 시도했으나, 해당 브랜치가 **원격 저장소 내부에 존재하지 않거나** 또는 **로컬이 최신 정보를 반영하지 못했을 때** 발생합니다.

| 용어 | 설명 | 문제 상황에서의 의미 |
| :--- | :--- | :--- |
| **Remote Ref** | 원격 저장소에 존재하는 특정 참조(Reference), 즉 브랜치 이름 자체를 의미합니다. | 로컬이 "저기 `main`이라는 이름의 가지가 있을 거야"라고 가정했지만, 실제 원격에는 그 이름의 가지만 존재하지 않습니다. |
| **`fatal:`** | 치명적 오류(Fatal Error)로, 해당 작업을 진행할 수 없어 Git 명령 자체가 중단됨을 의미합니다. | 단순히 경고를 넘어, 반드시 수정해야 하는 심각한 상태입니다. |

---

### 2. 주요 발생 원인 (Root Cause Diagnosis)
이 에러가 발생하는 가장 흔하고 구체적인 세 가지 시나리오는 다음과 같습니다.

#### A. 브랜치 이름 불일치 (Master vs Main) - **가장 높은 확률**
*   **원인:** 과거의 Git 설정에서는 기본 브랜치 이름을 `master`로 사용하는 것이 표준이었습니다. 최근 업계 트렌드에 따라 이를 `main`으로 변경하는 추세입니다. 만약 프로젝트가 아직 업데이트되지 않은 상태라면, 원격 저장소의 실제 이름은 `main`이 아니라 **`master`**일 가능성이 매우 높습니다.
*   **현상:** 로컬에서 `git checkout main`을 시도했으나, 원격에 `master`만 존재할 경우 발생합니다.

#### B. Synching 지연 또는 누락 (Stale Local Cache)
*   **원인:** 로컬 Git 클라이언트가 원격 저장소의 최신 브랜치 목록 정보를 받아오지 못했을 때 발생합니다. 마치 구식 지도에 새로운 길이 생겼는지 모르는 것과 같습니다.
*   **현상:** 최근 누군가가 `master`를 만들었지만, 내 컴퓨터는 아직 그 사실을 인지하지 못할 때 발생합니다.

#### C. 권한 또는 초기화 오류 (Initialization Error)
*   **원인:** 원격 저장소 자체가 제대로 초기화되지 않았거나, 브랜치에 대한 쓰기/읽기 접근 권한이 누락되었을 경우입니다. (다만 이 경우는 보통 다른 인증 에러가 함께 발생합니다.)

---

### 3. 필수 해결 방법 및 명령어 가이드 (Actionable Solution)
문제를 해결하기 위해 순서대로 다음 명령어를 실행하고, 그 결과를 보고하는 것이 가장 안전한 접근 방식입니다.

#### 💡 Step 1: 원격 브랜치 목록 확인 (가장 중요)
현재 로컬이 인지하고 있는 모든 원격 브랜치를 조회하여 실제 이름이 무엇인지 파악합니다.

```bash
git branch -r
```
*(예상되는 결과: `origin/master`, 또는 `origin/main`)*

# ⚙️ 기술 보고서: Git 오류 분석 및 해결 방안
## 에러 코드 정의: `fatal: couldn't find remote ref main`

### 1. 개요 및 원인 분석 (The What & Why)
이 에러는 로컬(Local) 개발 환경의 Git 클라이언트가 원격 저장소(Remote Repository, 예: GitHub)에 특정 브랜치 이름(`main`)을 찾으려고 시도했으나, 해당 브랜치가 **원격 저장소 내부에 존재하지 않거나** 또는 **로컬이 최신 정보를 반영하지 못했을 때** 발생합니다.

| 용어 | 설명 | 문제 상황에서의 의미 |
| :--- | :--- | :--- |
| **Remote Ref** | 원격 저장소에 존재하는 특정 참조(Reference), 즉 브랜치 이름 자체를 의미합니다. | 로컬이 "저기 `main`이라는 이름의 가지가 있을 거야"라고 가정했지만, 실제 원격에는 그 이름의 가지만 존재하지 않습니다. |
| **`fatal:`** | 치명적 오류(Fatal Error)로, 해당 작업을 진행할 수 없어 Git 명령 자체가 중단됨을 의미합니다. | 단순히 경고를 넘어, 반드시 수정해야 하는 심각한 상태입니다. |

---

### 2. 주요 발생 원인 (Root Cause Diagnosis)
이 에러가 발생하는 가장 흔하고 구체적인 세 가지 시나리오는 다음과 같습니다.

#### A. 브랜치 이름 불일치 (Master vs Main) - **가장 높은 확률**
*   **원인:** 과거의 Git 설정에서는 기본 브랜치 이름을 `master`로 사용하는 것이 표준이었습니다. 최근 업계 트렌드에 따라 이를 `main`으로 변경하는 추세입니다. 만약 프로젝트가 아직 업데이트되지 않은 상태라면, 원격 저장소의 실제 이름은 `main`이 아니라 **`master`**일 가능성이 매우 높습니다.
*   **현상:** 로컬에서 `git checkout main`을 시도했으나, 원격에 `master`만 존재할 경우 발생합니다.

#### B. Synching 지연 또는 누락 (Stale Local Cache)
*   **원인:** 로컬 Git 클라이언트가 원격 저장소의 최신 브랜치 목록 정보를 받아오지 못했을 때 발생합니다. 마치 구식 지도에 새로운 길이 생겼는지 모르는 것과 같습니다.
*   **현상:** 최근 누군가가 `master`를 만들었지만, 내 컴퓨터는 아직 그 사실을 인지하지 못할 때 발생합니다.

#### C. 권한 또는 초기화 오류 (Initialization Error)
*   **원인:** 원격 저장소 자체가 제대로 초기화되지 않았거나, 브랜치에 대한 쓰기/읽기 접근 권한이 누락되었을 경우입니다. (다만 이 경우는 보통 다른 인증 에러가 함께 발생합니다.)
